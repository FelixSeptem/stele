## Context

Stele already filters every repository query by tenant, project, and namespace,
but protected HTTP routes authenticate against process-local API-key allow lists
and then accept scope from request headers. A valid key can therefore claim an
ungranted scope. Event ingestion also creates a new raw event for every retry,
which can duplicate downstream governance work.

The implementation must remain PostgreSQL-only, OpenAPI-first, self-hostable,
and compatible with the existing `api`, `worker`, and `scheduler` modes. It
must not persist plaintext credentials, log secrets, or turn Stele into a
hosted identity service.

## Goals / Non-Goals

**Goals:**

- Authenticate protected HTTP requests as durable principals with bounded roles
  and credential lifecycle state.
- Authorize every requested tenant/project/namespace against explicit grants
  before handlers receive scope context.
- Provide a safe first-deployment bootstrap operator while transitioning normal
  access to durable principals.
- Make `POST /v1/events` exactly-once from a caller's perspective for an
  idempotency key and exact request payload, including stable replay of the
  original admission result.
- Preserve bounded audit history for access and idempotency decisions.

**Non-Goals:**

- OAuth/OIDC, end-user identities, a UI, SDK, hosted control plane, or external
  authorization service.
- Broad migration framework work, runtime request limits, or multi-scope
  maintenance redesign.
- Deleting canonical memory or changing the governed event-to-memory lifecycle.

## Decisions

### Decision 1: Store principals, grants, and credential digests in PostgreSQL

Add scoped principal records with stable IDs, `public` or `admin` roles, active
or disabled state, bounded labels, expiry timestamps, and append-only lifecycle
audit. Credentials are separate records that store a lookup-safe identifier,
salted one-way digest, status, expiry, creation/rotation/revocation timestamps,
and bounded actor/reason attribution. Scope grants explicitly store the exact
tenant/project/namespace each principal can access.

The raw credential is generated by the service, returned only once through an
admin create/rotate response, and never stored, logged, used as a metric label,
or included in audit metadata. A fixed prefix identifies the credential format;
the secret portion is hashed with a standard-library password/KDF-compatible
one-way construction. Lookup is performed against an indexed, non-secret key
identifier, followed by constant-time digest verification.

Alternative considered: retain environment allow lists and map each key to
scope in configuration. Rejected because grants, disablement, rotation, and
audit need durable operational state and cannot safely be managed across
replicas from process configuration alone.

### Decision 2: Scope headers select a grant; they do not create authority

Middleware first authenticates a principal, validates the required scope
headers, then checks an exact active grant for the requested scope and required
route role. It writes both principal and normalized scope to request context.
Handlers continue to consume `ScopeFromContext`, so repositories retain their
existing defense-in-depth filters.

Admin routes require the `admin` role. Public routes allow `public` or `admin`
principals with the requested scope grant. Authentication failure, expired or
disabled credentials, missing grant, and role mismatch return the same bounded
unauthorized/forbidden response shape and never reveal principal, grant, or
target-scope existence.

Alternative considered: infer scope from a principal's single grant and remove
scope headers. Rejected because integrations need to choose among several
authorized scopes; explicit headers are clear when they are authorization
checked.

### Decision 3: Bootstrap operator is explicitly constrained

`STELE_AUTH_BOOTSTRAP_ADMIN_KEY` configures one in-memory bootstrap operator
only when no durable admin principal exists. It is restricted to the configured
default tenant/project/namespace and can create the first durable admin
principal and grant. After a durable admin exists, bootstrap access is rejected
unless an explicit emergency override is configured and audited.

Existing `STELE_AUTH_API_KEYS` and `STELE_AUTH_ADMIN_API_KEYS` are deprecated.
They are not converted implicitly into arbitrary-scope principals. Startup
reports an actionable configuration error when legacy keys are configured
without the constrained bootstrap migration setting.

Alternative considered: preserve legacy keys indefinitely for compatibility.
Rejected because that preserves the authorization bypass this change exists to
remove.

### Decision 4: Event idempotency is a durable claim with a request fingerprint

`POST /v1/events` requires an `Idempotency-Key` header. The service validates
its bounded format, normalizes the request's event type, content, metadata, and
source timestamp into a deterministic request fingerprint, then creates or
reads an idempotency record under `(principal_id, tenant, project, namespace,
idempotency_key)`.

The idempotency record and raw event/provenance write occur in one PostgreSQL
transaction. A matching completed record returns the original event ID and
admission result. A key with a different fingerprint returns `409 Conflict`
without writing an event. In-progress claims use a short durable lease and are
either resumed after lease expiry or return a bounded retryable conflict; this
prevents ambiguous duplicate writes after process failure.

Alternative considered: unique key only on raw events. Rejected because it
cannot distinguish payload reuse conflicts or replay the original admission
decision safely.

### Decision 5: Principal administration stays under existing admin routing

Add admin-only endpoints for principal list/read/create, credential rotation,
disablement, and exact grant create/revoke/list. Responses expose IDs, bounded
role/status/timestamps, and grant scopes; list/read responses exclude raw
credentials and digests. Audit reads expose bounded action/status/timestamps
without credential material or free-form secrets.

## Risks / Trade-offs

- [Credential leak during create/rotate response] → return the raw key exactly
  once over authenticated TLS-facing API response; never persist it, and test
  logs/metrics/admin reads for absence.
- [Bootstrap operator lockout] → validate default scope and bootstrap key at
  startup; document first-principal creation and provide an explicit, audited
  emergency operator override rather than a broad legacy fallback.
- [Duplicate events during a crash] → transactionally couple claim/event/result
  persistence and lease in-progress claims with retry-safe recovery.
- [Authorization checks add database work] → index active credentials and exact
  grants; avoid in-process authorization caches in the first slice so disable
  and revoke take effect immediately across replicas.
- [Breaking existing integrations] → publish migration guidance, fail clearly
  for deprecated key settings, and provide a constrained bootstrap path.

## Migration Plan

1. Add PostgreSQL tables and indexes for principals, credentials, grants,
   audit records, and event idempotency records without removing old columns or
   changing memory records.
2. Add configuration validation and bootstrap operator support.
3. Deploy admin principal lifecycle endpoints; create an admin principal and
   grants for every existing integration scope.
4. Update public integrations to use durable principal credentials and include
   `Idempotency-Key` on event writes.
5. Enable principal-bound middleware, reject legacy unrestricted key lists, and
   monitor bounded authorization/idempotency metrics.

Rollback: retain all old memory data and disable newly issued principals if
needed. A rollback before enforcement can temporarily restore the prior
middleware only through an explicitly documented emergency configuration;
plaintext keys are never recoverable from the new credential store.

## Open Questions

- None for the first slice. The first implementation uses exact grants only;
  wildcard tenant/project/namespace grants and external identity providers are
  deferred until an explicit authorization model proposal.
